# 我是怎么用 AI 写公众号的

> 作者：艾AI
> 栏目：烨然漫笔 · AI 与人的处境
> 写作日期：2026-09-16

上一篇文章结尾，我留了一句话：这套「AI 干活、人把方向」的做法，改天专门写一篇。今天就来兑现。

先把边界说清楚，免得误会。这篇文章不教你用 AI 批量生产爆款——那件事我也不擅长。我要讲的，是我自己一点点摸出来的一套小流程：用 AI 帮着查证、排版、送草稿，但把「写什么、怎么写、发不发」这三件事，始终留在自己手里。

还要再交代一句，免得把话说大：写文章这件事我做了几个月，写作和排版的规矩也是一路磨出来的；但「自动把稿子送进草稿箱」这一环，其实是最近才跑通的，还在验证期。所以下面是一份刚刚跑顺、坑还热着的记录，不是什么成熟方案。

## 一、AI 替我干了什么，没干什么

很多人一提到「用 AI 写公众号」，脑子里是另一幅画面：给个标题，AI 哗啦吐出一篇，人复制粘贴，点发布。那是另一条路，也很常见。我走的不是这条。

我让 AI 干的，是四件边界清晰的事：

1. **查证**。写作前把每个数字、每处引用回到一手来源逐字核对，追不到就降级或删掉。
2. **排版**。把写好的内容分别做成两个版本：一个给网站，一个给公众号，后者要做到复制进编辑器样式不变。
3. **送草稿**。把公众号版推送到草稿箱，封面、摘要、阅读原文链接一次配齐。
4. **自检**。推送前跑一遍校验：标题长度、字数上限、有没有不该出现的脚本或占位符。

而这几件事，我没交给它：

1. **选题**。这篇文章该不该写，我自己定。
2. **判断**。哪个数据能用、哪个口径有风险，我自己拍。
3. **发布**。草稿进了后台，正式点下「群发」的那一下，是我按的。

一句话概括：AI 负责把动作做对，我负责把事情做对。动作可以交给机器，判断留给自己。

## 二、整条链路长什么样

用一次真实的发布流程来还原。它大致是五步：

**第一步，写作。** 先有母稿，一份纯文字的 Markdown，把想说的话完整写下来。这是整条链路的起点，也是唯一不依赖任何工具、纯靠人脑的部分。

**第二步，事实核查。** 这一步最花时间，也最不能省。我给自己定的规矩是：任何数字，先在一手机构页面找到，再进文章；二手聚合网站只用来找线索，不用来下结论。上一篇文章里那些「25%、3.3%、34%、11%」，都是这样一个个回到国际劳工组织官网逐字对出来的。

**第三步，双版本排版。** 同一份母稿，生成两个 HTML：一个是网站版，放在自己的域名下，保留完整的证据链——每条来源都可点击，还有方法说明和更新记录；另一个是公众号版，把核心观点完整讲清楚，但做成了复制进微信编辑器样式也不变的格式。

**第四步，推送草稿。** 公众号版经过校验后，通过微信接口送进草稿箱，封面、摘要、阅读原文链接一并配好。

**第五步，人工发布。** 我在后台打开草稿，手机预览一遍，确认排版和数据都没问题，再决定发不发、什么时候发。

这五步里，只有第一步和第五步需要我全程在场。中间三步，AI 可以配合完成——但它做的每一步，我都能看见、能叫停、能推翻。

## 三、三个让我印象最深的坑

工具和流程听起来都顺，真跑起来全是坑。挑三个最有代表性的讲。

**第一个坑：微信公众号的编辑器，会悄悄「吃掉」排版。**

我给文章配过两张数据图，用条形表示比例。在本地浏览器里看，比例完美；结果一进微信编辑器，九根条全变成了一样长。查了半天才发现：微信编辑器会忽略表格单元格上的百分比宽度，把两列重新均分。

这件事的教训比技术本身重要：**本地看起来对，不等于在微信里就对。** 后来凡是要在微信里呈现比例，我一律用微信能认的结构来做，而且草稿更新后还要在手机上再肉眼确认一遍。

**第二个坑：一个普通的编辑器，差点把文章撑爆。**

有一回，公众号版的 HTML 被某个带「页面节点追踪」功能的编辑器打开过。结果它悄悄给每个标签都加了一串追踪属性，文件凭空胖了一大截，正文字符数从一万九涨到两万六，直接超过了微信两万字符的上限。

发现之后我做的第一件事，是从版本库里恢复干净版本——比逐条删属性更彻底。这也是为什么我坚持把内容放进版本管理：**出了问题，能回到上一个对的版本。**

**第三个坑：AI 会把「能做成」误当成「该做」。**

有一次，整套流程跑通了，草稿也顺利进了后台。但临到发布，我停下来确认了一件事：这篇文章以前是不是发过？确认发过之后，我把它按下了。

这个决定没有任何技术含量，但它恰恰是整条链路里最值钱的一环。**工具能证明一件事能做，不能证明它该做。** 前者归机器，后者归人。

## 四、具体装了哪些 skill

我用的是 WorkBuddy。比「用了什么工具」更值得说的是这些 skill 的来历——七个里有六个是踩坑之后自己攒出来的，只有一个是现成拿来用的。这个比例大概就是实际情况：skill 不是装出来的，是攒出来的。

| skill | 干什么用 | 来历 |
|---|---|---|
| `wechat-canonical-draft-pipeline` | 主流水线：网站原文先上线，再把公众号版送进草稿箱，含幂等与校验 | 自己沉淀 |
| `ai-industry-article-fact-review` | 事实核查：数字、引用逐条回到一手机构页面 | 自己沉淀 |
| `wechat-compatible-article-html` | 公众号兼容排版：复制进编辑器样式不变 | 自己沉淀 |
| `wechat-cover-refinement` | 封面精简：文字太挤、层次不清时重做 | 自己沉淀 |
| `canvas-infographic-review` | 配图可读性审查：图表在手机上是否还看得清 | 自己沉淀 |
| `pre-opensource-sanitization-audit` | 发布前敏感信息审查：凭证、内部信息、个人路径 | 自己沉淀 |
| `humanizer` | 去掉 AI 写作痕迹，让文字读起来像人写的 | 现成的 |

沉淀 skill 的时机，基本都是踩了坑的当天。比如上面第一个坑——条形图被微信编辑器均分——修完之后，「比例类样式必须用微信认的结构实现」这条就写进了公众号排版那个 skill 里；第二个坑修完，「被污染的 HTML 优先用版本库恢复」也跟着进去了。所以这些 skill 现在读起来都有点像事故报告，而不像教程。

还有个我自己没料到的地方：这些 skill 里写得最多的不是「怎么做」，而是「不要怎么做」和「做完怎么验证」。真正会出事的地方，往往不是不知道该做什么，而是以为自己做对了。

## 五、微信后台那几项配置

「自动把稿子送进草稿箱」这一步最容易卡住，卡点基本都不在代码，在配置。记录一下我实际动过的地方：

1. **开发者凭证。** 在微信公众平台后台「设置与开发 → 基本配置」里拿 AppID 和 AppSecret。这两个串是程序调接口的钥匙，AppSecret 我是当密码存的，放在仓库外面，没写进代码或文章。

2. **IP 白名单。** 同一个后台有「IP 白名单」设置。程序调微信接口时用的是机器的出口 IP，这个 IP 不在白名单里，接口直接报 `40164`。我第一次撞上时还以为是代码写错了，查了一圈才发现是白名单。更麻烦的是这个 IP 会变——换个网络、换台机器都可能变。现在我看到 `40164` 的第一反应，是先去看当前出口 IP 是什么。

3. **只调草稿接口。** 微信把「保存草稿」和「群发」分成了两类接口。我只调前者，把文章送进草稿箱就停下，剩下的自己去后台点。这是刻意的——技术上完全能接着调发布接口，但我不想那样。

## 六、边界写在了规范里

这套做法稳定下来之后，我做了件看起来很「重」的事：把边界和纪律写进一份规范文件，当成唯一的标准，而不是靠记忆和默契。因为踩过的坑如果不写下来，就会再踩一遍。

规范里写得最清楚的一条是：

**自动化止于草稿箱，正式发布由人在后台人工确认。**

这不是技术做不到自动发布——接口是有的。而是我刻意把「最后一步」留给了自己。理由也简单：一旦把发布也自动化，人就从一个做判断的作者，退化成一个看结果的旁观者。而判断，恰恰是我最不想交出去的东西。

## 七、说到底，还是那个问题

写这篇文章的过程，本身就是我在说的这件事的一个样本：选题是我定的，结构是我搭的，哪些坑值得讲、哪些细节不能省，也是我判断的。AI 帮我查证、帮我排版、帮我检查，但它没替我做任何一个真正的决定。

所以回到上一篇文章的那句话——AI 时代最重要的问题，不是人还要不要劳动，而是劳动还是否属于人。

写公众号这件小事，也是一样的道理。AI 可以把字排得漂亮、把数据核得干净、把草稿送进后台。但一篇文章该不该写、写出来是不是自己想说的话、最后要不要按下发布，这些只能自己来。

工具越聪明，越要想清楚：哪些东西可以交给它，哪些东西得留在自己手里。

我选择把判断留给自己。

> 附：本文所描述的工具链与踩坑，均来自「烨然漫笔」的真实实践；涉及的公众号流程止于草稿箱，正式发布始终由我人工完成。文中提到的工具和 skill 是我自己在用的，不构成推荐，也没有任何合作或推广关系；除此之外不点名其他第三方产品，不虚构任何数据与效果。
